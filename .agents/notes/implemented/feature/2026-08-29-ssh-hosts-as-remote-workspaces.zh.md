# Agent Note：SSH 主机作为远程工作区

Status: implemented

[English](2026-08-29-ssh-hosts-as-remote-workspaces.md) | 中文

## 问题

「连接」页管理着 SSH 主机，工作区面却对它们一无所知：新建会话只能选本地文件夹，「有 SSH」始终没有变成「在那台主机上工作」。会话无法真正运行在远程目录里——工作区注册表会 realpath + stat 路径、沙箱从会话 cwd 解析可写根、fs 工具按本地路径设限、会话日志按本地 cwd 键控——字面的远程路径要么在创建时就失败，要么更糟：创建出一个悄悄在错误机器上干活的会话。

## 决策

远程工作区 = **本地锚点目录 + 模型可见子句**。每台启用的主机拥有一个锚点——真实本地目录（默认在系统临时目录下的 `dsh-remote-workspaces/<名称>`，可经插件 `remoteWorkspaceRoot` 配置改址），于是所有本地不变量继续成立。`workspace.create` 在 `{ path }` 之外接受 `{ sshHost: <名称> }`（二者恰选其一）：工作区控制器经由 terminal-ssh 提供的 `sshWorkspace` 服务解析名称，该服务备好锚点并返回其路径；此后工作区、会话 cwd、沙箱根与持久化键都是普通的本地事实。让会话「远程」的是 terminal-ssh 注册的 `ssh:workspace` 提示上下文：一个把会话 cwd 与清单锚点匹配、并指示 agent 通过 `terminal_open` 类型 `ssh:<名称>` 干活的子句——在首次组装请求时随运行时上下文快照落日志，不新增事件类型即满足模型可见 ⟺ 已落日志。选择菜单在添加项上方列出服务端清单中的启用主机（地球图标）；选中即创建锚定工作区并进入会话。

### 归属

锚点约定、清单投影与子句都归 terminal-ssh——SSH 能力的事实留在 SSH 包里。工作区控制器对它只做类型引用加项目引用，部署未组合 SSH 后端时大声失败（`ssh-workspace-unavailable`）。ui-workspace 在客户端读同一个 `terminal-ssh` 设置命名空间并自行拼写那一小段投影——客户端包不得对 Host 包做值导入，而服务端清单只有三个字段。

## 曾考虑的替代方案

- **用 `ssh:` URI 当工作区路径**：否决——所有消费者（realpath、沙箱、持久化键、按 cwd 相等的会话复用）都假设本地规范目录；把 URI 贯穿所有环节是一个远程文件系统项目，不是工作区功能。
- **只靠组合层**（把每台主机挂成预设 persona）：按主机组合会成倍增加，而且对 GUI 运行时新增的主机只字不提。
- **不加子句**：工作区会成一个空的本地目录，agent 还试图往里填东西；子句才是这个功能的牙齿。

## 后果

在工作区选择器里点一台主机，得到的会话在侧栏以主机名标注，且第一次请求就已被告知「通过它的终端在远程主机上工作」。本地 fs 工具仍然只管本地；两台机器之间的文件传输不在范围内（无 SCP）。锚点目录设计上始终为空，清单条目移除后可以安全删除。
